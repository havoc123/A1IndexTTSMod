## BPE 热词补全：仅离线验证

用户要求本轮不启动游戏；本轮全部验证使用离线工具，未进行新的游戏 UI 测试。工具直接编译生产的 `AsrBpeTokenizer`、`AsrDecoderSession`，使用本机安装的 sherpa-onnx 1.13.8 CUDA 原生库。

分词资源来自同作者 XL 模型固定 revision `0128977216bda3dc2b7d70178be8e721c0e49b8b`，263,956 字节，SHA256 `867a7355801cb43939962ad757ba1cb7941b6171b5a6902772483b4e3a623377`。该资源的前 2,000 个 piece 与准确档 token 表逐 ID 匹配，XL 与准确档的完整 2,002 行 token 表逐行相同，原文件哈希差异是换行格式。安装器下载且固定散列；正式插件无 Python/protobuf 或额外推理模型依赖。

开发机用官方 Python SentencePiece 对生产适配器的 `--tokenize-only` 输出逐词比较：94 个句首路径和 94 个句中路径合计 188/188 一致，无未知 token，全部可还原原词；句中参照通过关闭官方 tokenizer 的 add_dummy_prefix 获取。另逐项核验 188 条原生别名路径映射回原模型 ID，全部一致。真实原生 recognizer 带词表成功初始化和解码；调试日志没有 OOV 或热词编码失败。坏模型 SHA256 和错位 token ID 的负例均在加载 CUDA 前明确拒绝。

标准 `bpe` 热词入口自动添加 `▁`。实际合成录音的 token 轨迹只在整段开头有该标记，句中不存在；仅设置该入口虽能加载 94 个词，却与关闭热词的识别结果完全相同。最终适配器为每词构造句首和句中两个原始 ID 路径，共 188 条；以派生 token 别名通过固定版本的字符入口送入上下文图。原始 token 文件和权重不变，结果 token 始终保留原始拼写；生产路径增加私用区别名泄漏断言。相关实现依据为 [原生 SymbolTable 首个 ID 拼写行为](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/sherpa-onnx/csrc/symbol-table.cc) 与 [热词完整路径匹配](https://k2-fsa.github.io/sherpa/onnx/hotwords/index.html)。原生库升级需要重跑该测试。

路径审计还捕获了 16 个词的词首标记融合问题：其首 token 是 `▁` 加汉字，不能直接删除首 token。最终句中路径重新对无前缀原词编码，避免丢字；中间探测版本仅生成 172 条路径，不作为最终交付。

正例由本机 Windows `Microsoft Huihui Desktop - Chinese (Simplified)` 合成，SAPI PCM 22,050 Hz、16-bit mono，工具重采样至 187,143 个 16 kHz 样本。合成文本为“苏倾盏。焚天宗。我想找苏倾盏，去焚天宗看看。念乔。今天吃了一个苹果。”；以下 CER 对比的是去标点后的 28 字合成输入文本，并非真人口音测评。
